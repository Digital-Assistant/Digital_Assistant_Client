# AGENTS.md - Digital_Assistant_Client

Browser extension UI (Chrome, Manifest V3) for the Universal Digital Assistant Network. The core logic is the published npm package `@udan/digital-assistant-sdk` (pinned to an exact version); this repo holds the UI, the content scripts and the background worker. **This repo is public.** Workspace rules (branches, Docker scripts, agent-agnostic files) are in the workspace `AGENTS.md`; this file covers only this repo. `CLAUDE.md` is a one-line import of this file.

## Public-repo rule
- Never commit or print private values: hostnames of the real backends, AWS account ids, Parameter Store paths, secrets, tokens. Describe them by role ("the TEST backend").
- Backend URLs reach the build only as Actions **variables** (organization level, shared with the SDK repo) or from a gitignored `environments/<build>.env`. Never as secrets, never in tracked files.
- Everything inlined into the extension can be read by anyone who unzips it. Secret keys (`keycloakClientSecret`, `profanityKey`, `googleTranslateApiKey`, `googleAnalyticsSecretKey`, `clientSecret`) must have no value in any env file; `scripts/ci/check-env-keys.sh` fails the build otherwise. Never ship, release or upload a zip built with a secret.

## Commands (Node 22)
- `npm ci` (or `npm install`), then `npm run build:prod` -> `dist/` (not committed); `npm run build` -> `build/`; `npm start` watches; `npx tsc --noEmit` is the type check.
- There is no unit-test suite. CI checks: build and pack, type check, gitleaks, workflow lint, `npm audit` (report only).
- `npm run e2e:behaviour -- --build <dir> --backend <url>/api` runs the 14 behaviour checks against a local stack (README "Behaviour check (local stack)"). Not in CI. It needs a build that can sign in: `--auth keycloak-pkce` needs only `keycloakPublicClientId`, `--auth chrome-identity` a secret that never comes from this repo.
- `scripts/ci/*`: the workflows only call these scripts, run them locally the same way. Index and details: `scripts/ci/README.md`.
  - `package-extension.sh` builds once and writes `out/udan-extension-<X.Y.Z.N>.zip`, `SHA256SUMS`, `build-info.json`.
  - `generate-env.sh`, `check-env-keys.sh`, `lint-workflows.sh`, `latest-client-build.sh`, `publish-test-build.sh`, `smoke-extension.sh`.
- `webpack` is pinned at 5.112.2. Retried 2026-10-28 in a scratch install: 5.112.2 builds the SDK bundle and passes the smoke check, so the old 5.105.4 pin (5.112.0 failed) and the Dependabot ignore for webpack are gone. Bump it only through a PR that passes the smoke check. `buffer` and `process` are direct dependencies on purpose (webpack `ProvidePlugin`).
- Build health: `drop_console` applies to `build:prod` and `build:qa` only (`isProd` in `webpack.config.js`); `.gitattributes` has `* text=auto eol=lf` (CRLF checkouts made noisy diffs; compare old trees with `git diff --strip-trailing-cr -w`); the old `antd` alias is gone.

## Environment settings
- Schema = `environments/env.example` (14 public keys, each URL as a `Prod`/`Test` pair). Add a new key to `env.example` only (`scripts/build-env.js` and `generate-env.sh` read the schema; the UPPER_SNAKE Actions variable must also exist) and say so in the PR. Values come from `environments/<build>.env`, or an environment variable with the key's own name.
- Runtime choice of TEST or PROD (page key, options override, install type, default PROD) lives in `src/config/runtimeEnvironment.ts`; read the README section "TEST or PROD at runtime" before changing it. A host page must call `UDAPluginSDK` after the `UDASdkReady` event.
- Auth and config (details in README "Sign-in and where the config lives"): sign-in runs in the worker, started by the Sign-in button (`RequestUDASessionData` with `UDASignIn`). A Chrome identity uses the old flow (`LoginWithBrowser`, token service, needs `clientSecret`; kept until PK15) only when the build carries that secret (a local test build; no shipped build does); otherwise, if the build has `keycloakPublicClientId`, Keycloak authorization code + PKCE (`LoginWithKeycloak`, `launchWebAuthFlow`, no secret, `kc_idp_hint` defaults to `google`). A Chrome-signed-in tester with a secret-less build must still reach Keycloak (2026-10-30: routing them to the old flow made the button dead). The refresh token stays in the worker (`chrome.storage.local`); the panel gets the access token only and renews it through the worker (SDK host-token API). Never add a Keycloak `check-sso` on load, and never open a sign-in window without a user action. Config reaches the worker only through `buildConfig.ts`; a host page cannot set it. The SDK needs `realm` and `clientId` and sends nothing without them. The panel shows sign-in problems in plain words from `UDAAlertMessageData` codes (`AuthContext`, README "Sign-in screen and messages"). Test procedure and the 14-check behaviour list (plus the sign-in UI extras): README "Testing a change locally".
- Manifest changes (permissions, `action`, `options_ui`, `key`) need the owner's OK. `key` in `public/manifest.json` is the public half of the dev/TEST key pair (owner OK 2026-10-29): it pins the extension id `lcnkfnijlogkgifbfhkcnmndhabnloco`, and so the Keycloak redirect URI. The private key never enters the repo. A store upload must drop `key`. Firefox is not supported.

## Branches, releases, rollback
- Branch from `dev`, PR into `dev`, Conventional Commit PR title (`feat:`, `fix:`...). No commit, push or PR unless the owner asks. Never touch `master`.
- CI builds one zip per `dev` push (artifact `client-zip`, 90 days). `Deploy to TEST` (manual, `dev` only) publishes that same zip as prereleases `test-v<version>` and `test-current` and never rebuilds; rollback = run it with an older `version`. Release Please owns `package.json` and `CHANGELOG`, CI owns the extension version in the built manifest (`X.Y.Z.<run>`).
- Merge method: squash (PR title becomes the commit; the repo also allows merge and rebase, but use squash into `dev`; `dev` to `master` is a merge commit). Default branch is `dev`: GitHub registers `workflow_dispatch`-only workflows (like `Deploy to TEST`) only from the default branch, so keep it `dev`.
- Unpacked installs never auto-update: testers remove the old extension and load the new folder.
- The SDK pin changes only through a PR; the SDK is promoted to npm `latest` after a Client TEST pass (SDK `RELEASE_PROCESS.md`).
- Chrome Web Store upload and the SDK CDN feed are not built yet (track phases C08, C09).

## Dependabot and lockfile lessons
- npm minor/patch updates are grouped into one weekly PR (`.github/dependabot.yml`); majors stay separate. Merge a Dependabot PR only when `gh pr view --json mergeStateStatus` says `CLEAN` (checks green and up to date), not just when checks are green.
- `package-lock.json` is tracked; `npm ci` fails without it. On a lock conflict take the branch's lock and run `npm install --package-lock-only`; a lockfile older than a `package.json` change cannot be fixed by asking Dependabot to rebase (it compares commits, not lock content). Retitling a Dependabot PR stops it rebasing; rebase first, retitle after.
- Dependabot's lock regeneration drops `node_modules/@udan/digital-assistant-sdk/node_modules/react` (18.3.1, an optional peer entry). Symptom: `build` and `typecheck` fail on the PR with `npm ci ... Missing: react@18.3.1 from lock file`, and a rebase does not fix it because the entry disappears each time Dependabot rewrites the lock. Fix on the PR branch: merge `origin/dev`, copy that one entry back from dev's lockfile, verify `npm ci --dry-run` resolves, then push and let CI Gate run. Never paper over it with `--legacy-peer-deps`, and never take the branch's lock wholesale — it is the file that is missing the entry. Every new npm Dependabot PR after a `dev` change repeats this.
- A green PR that is `BEHIND` is still blocked: the `Protect dev` ruleset sets `strict_required_status_checks_policy: true`. Run `gh api -X PUT repos/Digital-Assistant/Digital_Assistant_Client/pulls/<n>/update-branch`, wait for `CI Gate` to report again, then squash-merge. Merging one PR re-behinds every other open PR, so update them in the same round.
- Do not run two `gh` processes at once; the local `gh` cache can corrupt.
